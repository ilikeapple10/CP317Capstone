Sprint Goal
Sprint objective: Deliver a working first prototype of the E-commerce marketplace where a shopper can search the catalog, manage a cart and checkout, create an account (with data-collection consent) and login, and a seller can manage their product listening, all connected to a shared database through a Flask REST API and an Angular frontend.


Why these items were prioritized:
* Search and cart are the core buyer partner. Every later feature (product pages, wishlist, order tracking, reviews) depends on products, being listed, found, and added to a cart 
* Accounts and login unlock everything role-specific. Sellers, order history, and wishlists all need a signed-in-user, so authentication had to come first.
* Consent was flagged as a high priority in Milestone 02. Our ethical considerations required the constant notice to exist before any real user data is collected, so it was built together with account creation
* Seller listing supplies the catalog. Without a way for sellers to add products, the marketplace has nothing to sell
* Three of the stories (UI-1, UI-3, INV-2) are rated High priority in our backlog. USER-2 is medium but sellers need an account before they can list products, so it had to come in Sprint 1 with INV-2
* These stories also let us set up the full stack (database -> Flask API -> ANgular UI) in one sprint, which later sprints build on

Implementation Progress
What was built
Backend (Flask + SQLlit)
* SQLlite database with products, accounts, and other table, created and seeded on startup
* A JSON REST API with CORS enabled for the Angular dev server, using session cookies for cart and login state.
* Keyword + category product search, session cart with stock limits, consent flow, account creation with hashed passwords, login/logout, seller-only listing management, and order placement.
Frontend (Angular)
* Products page (search bar + category dropdown) connected to the backend
* Cart page and a shared Header component showing the cart count.
* Login and Signup pages with show-password tottle, confirm-password check, and “continue as guest”
* Seller dashboard (load, add, remove listings) protected by a route guard.
* Order page showing order history after checkout
* A shared colour palette guide for consistent styling across components

Password Hashing (salted PBKDF2, never stored in plain text):
def hash_password(password, salt=None):
   if salt is None:
       salt = secrets.token_hex(16)
   digest = hashlib.pbkdf2_hmac("sha256", password.encode(), salt.encode(), 100_000).hex()
   return f"{salt}${digest}"

Technical Issues and how they were resolved


Issue
	Resolution
	The Angular app (port 4200) and Flask API (port 5050) run on different origins, so browser requests were blocked and session cookies were not sent
	Enabled CORS for localhost:4200 with credentials in Flask, and sent every request with  withCredentials: true true in Angular HttpClient
	After signing up, the user was not kept logged in and the signup form failed in the local Angular + Flask setup
	Fixed session handling so the session is set on account creation and cookies persist across requests
	Role naming was inconsistent between the frontend and backend (“customers” vs “shopper”)
	Standardized on shopper and seller across the database, API and UI.
	“Continue as guest” and the confirm-password check on signup did not work correctly 
	Fixed in the Signup component; guest can now search and use the cart without an account 
	The /seller page could be opened by anyone even through the API rejected non-sellers
	Added an Angular route guard that calls /api/seller and redirects non-sellers to the login page

Testing and Review

   * The cart and consent flow works through the JSON API

How acceptance criteria were checked
Each story’s acceptance criteria from Milestone 02 backlog were turned into a checklist. Criteria that can be automated (search results, stock cap, consent gate, role checks) are covered by the unit test above. The rest (page layout, navigation, form feedback) were checked manually by the developers and then demonstrated to the Product Owner, who marked each story Done or Pending in the backlog
